# מדריך בדיקות — התחלה ושימוש יומיומי

בדיקה אוטומטית מבצעת פעולות ומוודאת תוצאה צפויה. ירוק אומר שהתנאים שנבדקו התקיימו בסביבה הזאת; אדום אומר שיש פער שצריך לחקור. תוצאה ירוקה אינה הבטחה שאין באגים אחרים.

## התקנה ראשונה

הפרויקט משתמש ב־Bun 1.3.12. מתוך תיקיית הפרויקט:

```bash
bun install --frozen-lockfile
bunx playwright install chromium firefox webkit
```

בלינוקס/CI השתמשו ב־`bunx playwright install --with-deps chromium firefox webkit` כדי להתקין גם ספריות מערכת. אין צורך להגדיר Google או שרת אמיתי עבור הבדיקות.

## מה להריץ

| פקודה | מה קורה |
|---|---|
| `bun run check` | lint, טיפוסים, קישורי תיעוד ובדיקות יחידה; בלי דפדפן או build |
| `bun run test:unit` | בדיקות מהירות של סכמות, הרשאות, session, בקשות והידרציה |
| `bun run test:ui` | ממשק Playwright לבחירת בדיקה, הרצה ועיון בצעדים; שרת פיתוח מבודד |
| `bun run test:e2e` | build מקומי והפעלת המסלולים במחשב ובמובייל באמצעות Chromium |
| `bun run test:report` | דוח HTML של ההרצה האחרונה |
| `bun run test:release` | הערכה הרגילה וגם מסלולי ליבה ב־Firefox וב־WebKit |
| `bun run check:docs` | קישורים מקומיים בתיעוד פעיל |
| `bun run audit:security` | התראות תלויות High/Critical; בלי החרגות שקטות |

אחרי תיקון קטן הריצו `check` ואת הבדיקה הרלוונטית. אחרי שינוי עיצוב הריצו גם דפדפן ובדקו את הצילומים, מובייל, מקלדת ושתי ערכות נושא. לפני שחרור רגיש הריצו `test:release` ובדיקות ידניות מול סביבת staging.

## ההרצה הראשונה בממשק החזותי

1. הריצו `bun run test:ui`.
2. בחרו `smoke.spec.ts` ואחת משלוש בדיקות ההיכרות: דף הבית, פתיחת דוגמה או שגיאות בטופס.
3. לחצו על המשולש להפעלה. הרשימה מראה כל פעולה, והחלון מציג את מצב העמוד באותו שלב.
4. אפשר להפעיל בדיקה אחת שוב, לסנן לפי שם או פרויקט ולהריץ את כל הקובץ.
5. סגרו באמצעות Ctrl+C בטרמינל. Playwright סוגר את שרתי הבדיקה שהוא הפעיל.

מצב UI משתמש ב־dev לשיפור זמן התגובה, ומתחבר מחדש לשרתי הבדיקה שבפורטים הייעודיים בעת סריקת קבצים; אין להפעיל שם שירות אחר. הרצה אוטומטית משתמשת ב־build שחרור ודורשת פורטים פנויים. עצרו הרצה אחת לפני פתיחת השנייה: שתיהן משתמשות באותם פורטים ובאותו פלט מבודד.

## בדיקה אחת דרך הטרמינל

```bash
bun run test:e2e tests/e2e/smoke.spec.ts --project=chromium
bun run test:e2e --project=chromium -g "pagination"
bun test --preload ./tests/unit/setup.ts ./tests/unit/schemas.test.ts
```

לחקירת כישלון אפשר להריץ את אותו קובץ עם `--debug` או `--headed`. אין להוסיף השהיות שרירותיות כדי להסתיר בעיה; מחכים לתוצאה מסוימת, למשל הופעת כותרת או הודעת שגיאה.

## איך חוקרים אדום

הריצו `bun run test:report`, בחרו את הבדיקה האדומה וקראו את הפעולה הראשונה שנכשלה. עיינו ב־Expected מול Actual, צילום המסך ו־Trace. ב־Trace רואים את העמוד לפני ואחרי הפעולה ואת בקשות הרשת. הנתונים בדוח הם בדויים.

- `expect` או פעולה שלא מצאה רכיב: בדקו אם התנהגות האתר השתנתה, אם יש באג או אם שם נגיש השתנה במכוון. אל תעדכנו ציפייה רק כדי לקבל ירוק.
- כשל `webServer`, פורט תפוס או דפדפן חסר: הבדיקות טרם הגיעו לאתר. עצרו את הרצת הבדיקות האחרת או התקינו דפדפנים; אין לעצור שרת פיתוח לא קשור.
- `503` בתרחיש כישלון מכוון: צפוי שהשרת ידווח שגיאה. הבדיקה אמורה לוודא שהמשתמש מקבל משוב ושהמידע שלו נשמר.
- כישלון שנעלם בניסיון חוזר: עדיין דורש חקירה. CI מדווח ניסיונות חוזרים ונכשל גם על בדיקה לא יציבה.

`test-results/` שומר צילומים ו־trace לפי בדיקה. `playwright-report/` שומר את הדוח. ההרצה הבאה עשויה להחליף אותם; העתיקו אבחון נחוץ לפני הרצה נוספת. התיקיות אינן נכנסות ל־Git. אפשר לפתוח trace ידנית עם `bunx playwright show-trace <path-to-trace.zip>`.

בדיקות הנגישות שומרות צילומים בהירים וכהים לעיון בדוח; אין השוואת פיקסלים מחייבת לכל עמוד. axe בודק את התוכן הראשי וחלון ההרשמה במצבים שנבחרו, ואינו אישור נגישות מלא לאתר או לתוכן חיצוני.

## איך הסביבה מבודדת

Playwright מפעיל Core API מדומה ב־127.0.0.1:4100 ואת האתר ב־localhost:3100. פלט Next נמצא ב־`.next-e2e`, וקובצי עזר ב־`.cache`. שרת הפיתוח הרגיל ב־3000 אינו חלק מהבדיקות. הסביבה דורסת ערכי שרת ואימות שהורשו מהמחשב בערכי בדיקה.

ה־API המדומה מקבל גם פניות RSC ו־Server Actions. הוא מספק סיפורים ומשתמשים בדויים, שגיאה, תשובה לא תקינה, השהיה ותוצאות ריקות. כל בדיקה מאפסת נתונים; ההרצה טורית. משתמשים חתומים בעזרת קוד הבדיקות בלבד — אין נתיב כניסה עוקף באפליקציה.

החיפוש נבדק מבחינת פרמטרים, עימוד, הצגה ומרוץ בקשות; דירוג ורלוונטיות של מנוע השרת אינם נבדקים כאן. מדיה חיצונית מוחלפת בתוכן יציב.

## מה נשאר לבדיקה ידנית

- Google OAuth אמיתי: popup, cookies, השלמת הרשמה ויציאה בסביבת staging.
- אינטגרציה עם ה־Core API האמיתי, בלי נתוני production בבדיקות כותבות.
- מכשיר פיזי, מקלדת/קורא מסך, zoom, תחושת העיצוב ומצבי hover/focus/disabled/loading/error.
- תוכן חיצוני: Google Form, וידאו, WhatsApp וקישורים כאשר שונו.
- ב־macOS 14, WebKit הקפוא 2251 אינו תואם לפרוטוקול Playwright 1.64: יצירת עמוד נכשלת ב־`PushAPIEnabled` עוד לפני האתר. זאת [תקלה מתועדת בכלי](https://github.com/microsoft/playwright/issues/42964). `test:release` מציג הסבר ונעצר מוקדם במערכת הזאת; הוא אינו מדלג בשקט על WebKit. אימות מלא דורש CI Linux או macOS 15 ומעלה, ובנוסף מכשיר אמיתי.

לאימות מקומי חלקי במערכת הזאת בלבד:

```bash
bun run test:release --project=chromium --project=mobile-chromium --project=firefox
```

מעבר הפקודה החלקית אינו אישור שחרור מלא ואינו מאמת WebKit.

## הוספת רגרסיה

באג משמעותי מקבל בדיקה שמדגימה את הכשל לפני התיקון ואת ההתנהגות התקינה אחריו. העדיפו שמות משתמש ותוצאה, `getByRole`/`getByLabel`, ונתונים קטנים ב־`tests/fixtures`. אל תבדקו את ה־CSS הפנימי במקום ההתנהגות. שינוי מדיניות או זרימה מעדכן גם את המפרט הנוגע אליו.

## Hooks ובדיקות לפני קומיט

`bun install` מפעיל Husky. ה־pre-commit בודק את התוכן שב־Git index, כולל שמות עם רווחים וקבצים שהוכנסו באופן חלקי; הוא אינו משנה קבצים ואינו מבצע stash. הוא מריץ lint לקוד שנכנס לקומיט ובודק קישורי תיעוד מול קבצים שנכללו ב־index. טיפוסים, בדיקות יחידה ו־build שייכים ל־check/CI, ולא לכל קומיט קטן.

## בדיקות ב־GitHub

[Quality](../.github/workflows/quality.yml) רץ בכל דחיפה ל־`main`, בכל Pull Request ובהפעלה ידנית. אפשר לעבוד ישירות על `main`; ענף ו־PR הם אפשרות לפי גודל השינוי. ה־workflow מריץ בדיקות בלבד ואינו פורס את האתר.

| Check | תוכן |
|---|---|
| `Checks` | lint, טיפוסים, קישורי תיעוד ובדיקות Bun |
| `Dependency audit` | התראות תלויות High/Critical |
| `Browser tests` | build מבודד ובדיקות Chromium במחשב ובמובייל מול API מדומה |

ב־GitHub פתחי Actions → Quality ובחרי הרצה כדי לראות איזה שלב נכשל. דוח הדפדפן והצילומים נשמרים ב־Artifacts לשבעה ימים, כולל trace בעת כישלון. ניסיון חוזר אינו מסתיר בדיקה לא יציבה: גם מעבר רק בניסיון חוזר מכשיל את ההרצה.

לבדיקת שחרור מלאה בחרי Run workflow וסמני `release` להוספת Firefox ו־WebKit בלינוקס. לאחר העלאת תצורת CI חדשה יש לוודא שההרצה עובדת בפועל; [סטטוס האימות](planning/project-quality-foundation.md) מתעד מה כבר נבדק. הגנת ענף היא אפשרות נפרדת בהגדרות GitHub.
